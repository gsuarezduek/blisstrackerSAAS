## Arquitectura backend

### Backend (`backend/src/`)
- **Express + Prisma + PostgreSQL.** Entry point `index.js` imports the Express app from `app.js`. Routes are mounted under `/api/<resource>`.
- **Auth:** JWT (12h expiry) stored in `localStorage`. Google OAuth 2 via `google-auth-library`. The `auth` middleware attaches `req.user` (decoded JWT payload).
- **Invariante de los JWT — un token de propósito acotado NO es un token de sesión.** `lib/jwt.js` `verifyToken` (compartido por el middleware `auth` y el handshake de Socket.IO) acepta **sólo** tokens sin el claim `purpose`, y todo JWT acotado firmado con `JWT_SECRET` lo lleva: `client-portal-live`, `client-portal-magic`, `google-link`, `oauth-state` (`lib/oauthState.js`, el `state` de Google/Meta/TikTok/LinkedIn) y `mfa` (`lib/mfaChallenge.js`, el paso intermedio del login con 2FA). **Al agregar un JWT que no sea de sesión: ponerle `purpose` y validarlo donde se consume.** Antes esto era una lista **negra** de un solo valor (`client-portal-live`), así que cualquier token acotado nuevo nacía sirviendo también como token de sesión: `resolveWorkspace` resuelve la membresía con el header `X-Workspace` + el `userId` del token, **no** con el `workspaceId` del token, así que bastaba con que trajera `userId` para habilitar todas las rutas de nivel `member` (las admin-only fallaban por falta del claim `role`). El `state` de OAuth era el caso más expuesto: viaja en el query string de la URL del proveedor. La inversión a lista blanca fue **prerrequisito** del 2FA — sin ella el `mfaToken` habría sido un bypass completo del segundo factor (contraseña → `mfaToken` → usarlo como Bearer). Tests en `tests/unit/tokenPurpose.test.js`.
- **Workspace middleware** (`middleware/workspace.js`):
  - `resolveWorkspace` — reads `X-Workspace` header → looks up `Workspace` → attaches `req.workspace` + `req.workspaceMember`. Requires an active `WorkspaceMember` row for **every** user, `isSuperAdmin` included — a super admin who isn't a member of a workspace gets 403 here, same as anyone else.
  - `workspaceAdminOnly` — verifies `req.workspaceMember.role === 'admin' | 'owner'`.
- **Super admin** — `User.isSuperAdmin Boolean` is a global flag. The `superAdminOnly` middleware in `superadmin.routes.js` gates the internal panel (`/api/superadmin/*`), completely separate from `resolveWorkspace`/`workspaceAdminOnly`. **`isSuperAdmin` never elevates a user's permissions *within* a workspace** — `workspaceAdminOnly`, `isSalesUser`/`salesGuard` (role part), `projectAccess.isAdmin`, `GET /auth/me`'s `isAdmin`, chat moderation, and lead-note deletion all key off the real `WorkspaceMember.role`, not `isSuperAdmin`. A super admin who happens to be a plain `member` of a workspace is treated as a plain member there — same as any other user. To act with elevated access in a workspace they don't belong to (or belong to with a lower role), staff must use **Impersonar** from the Super Admin panel (`POST /api/superadmin/impersonate`), which issues a token carrying the *target* member's real role and `isSuperAdmin: false`. The only remaining `isSuperAdmin` bypasses are orthogonal to workspace role: billing-status write locks (`past_due`/`suspended`, `resolveWorkspace`) and feature-flag gating (`requireFeatureFlag`, the flag-check inside `salesGuard`) — both let staff preview/operate a module regardless of billing or flag grants, but only once they've already cleared the (now un-bypassed) membership and role checks.
- **Tests:** Jest + Supertest. `jest.config.js` at backend root. All tests in `backend/tests/`. Prisma is mocked with `jest.mock('../lib/prisma')` — no real DB needed.
- All dates for workday logic use `America/Argentina/Buenos_Aires` (UTC-3). Task timestamps are stored in UTC.
- **Email** is sent via Resend HTTP API (`src/services/email.service.js`) — not SMTP. (Excepción: el módulo **Mailing** manda con el Resend o el SMTP **del cliente**, por `services/mailing/providers/` — nunca con la key de la plataforma; ver `../docs/claude/mailing.md`.) Every send (success or failure) is logged to `EmailLog`. Each email function accepts an optional `workspaceId` as last parameter for the log.
- **URLs públicas: nunca armarlas a mano.** `src/lib/publicUrls.js` es el criterio único de las TRES bases, que desde la separación del sitio público son distintas: `siteUrl()` el sitio público (el apex, canónico — landing, precios, legales, blog), `appUrl()` la app (`app.<APP_DOMAIN>` — login, registro, `/join`, bajas de mailing, `/oauth-result`) y `workspaceUrl(slug)` el subdominio de la agencia; más `oauthReturnBase(slug)` para los retornos de OAuth/Stripe. Un `https://${process.env.APP_DOMAIN}/login` escrito a mano hoy apunta al sitio público, que **no tiene** esa pantalla. Tests en `tests/unit/publicUrls.test.js`; detalle en `../docs/claude/sitio-publico.md`.
- **Prisma singleton** at `src/lib/prisma.js` — all controllers import from here.
- **Stripe singleton** at `src/lib/stripe.js` — returns `null` if `STRIPE_SECRET_KEY` is missing; all billing code checks for null before calling Stripe.
- **Prisma error helper** at `src/lib/prismaError.js` — `handlePrismaError(err, res)` maps P2025→404, P2002→409, P2003→400.
- **Shared utilities:** `src/utils/dates.js` exports `todayString()` (Buenos Aires timezone). `src/lib/monthUtils.js` exports helpers de meses (`monthBounds`, `prevMonthStr`, `prevMonthsArr`, `monthLabel`, y `periodMonths`/`periodLabel` para períodos calendario de objetivos). `src/lib/objectiveCatalog.js` es el catálogo único de métricas de objetivos (categoría, unit, direction, aggregation flow/stock, param requerido).
- **Shared task include:** `tasks/_shared.js` and `workdays.controller.js` each define a `taskInclude` constant (`{ project, createdBy, _count: { comments }, sessions, checklist, contentPiece: { select: { id, scheduledDate } } }`) used in all task queries. `contentPiece` is only non-null for tasks created via Contenido's "Enviar al dashboard" — `TaskCard.jsx`/`NowCard.jsx` use it to render a 📅 "Contenido · publica <fecha>" badge (urgent/red if `scheduledDate` is today or past, via `fmtPublishDate` in `utils/format.js`) linking to `/contenido?projectId=&piece=` (same URL shape as the `CONTENT_MENTION`/`CONTENT_APPROVED` deep-links in `NotificationBell.jsx`), so working the task and jumping straight to the piece doesn't require navigating Contenido → project → piece manually. `scheduledDate` also drives the Backlog's ordering (ver "Dashboard" en `../CLAUDE.md`): content tasks sort by nearest publish date first, ahead of the normal createdAt order.
- **Weekly AI report** at `src/services/weeklyReport.service.js` — generates productivity analysis with Claude Haiku, sent every Friday at 00:01 ART via `node-cron`. Sequential processing with 3s delay between users. Solo respeta el tope **mensual** del workspace (`hasTokenBudget`); el semanal `Project.aiWeeklyTokenLimit` se sacó a propósito (salteaba el informe en silencio).
- **Insight memory** at `src/services/insightMemory.service.js` — weekly learning profile per user (tendencias, fortalezas, areasDeAtencion, estadisticas) using Claude Haiku. Updated every Saturday at 00:00 ART.
- **GEO audit** at `src/services/geoAudit.service.js` — fetches URL with axios + cheerio, analyzes with Claude (claude-haiku), stores result in `GeoAudit`. Async: controller returns auditId immediately, analysis runs via `setImmediate`. Progress tracked via `errorMsg` field during `running` status. Score 0–100 with 4 bands (Crítico/Base/Bueno/Excelente). Checks 23 AI crawlers (citation vs training), llms.txt, robots.txt, JSON-LD schema.
- **Feature flag catalog** at `src/config/featureFlags.js` — array of `{ key, name, description, stage }`. On server start, all flags are upserted to DB automatically. Never create flags manually from SuperAdmin UI — define them in code. `stage` separa dos paneles en SuperAdmin: `'module'` (estable, el sync de arranque fuerza `enabledGlobally=true` — panel **Módulos**, de solo lectura) vs `'testing'` (opt-in manual por workspace, panel **Feature Flags** de siempre). El controller (`featureFlags.controller.js` `update`) rechaza con 400 cualquier intento de tocar `enabledGlobally`/`enabledWorkspaceIds` de un flag `'module'`. Flags actuales: `marketing`/`eos`/`gamification`/`contenido`/`rrhh`/`calendario` en `'module'`; `ventas`/`whatsapp`/`finanzas`/`mailing` en `'testing'` (CRM y sus submódulos — WhatsApp de Ventas, y Finanzas — siguen en validación). `rrhh` ya traía `enabledGlobally:true` desde antes de existir `stage` (sembrado manualmente porque todos los workspaces ya lo usaban sin flag, ver concepto "RRHH panel") — con `stage='module'` ese estado queda estructural en vez de un seed manual.
- **Token budget** at `src/lib/tokenBudget.js` — presupuesto mensual de tokens de IA por workspace. `Workspace.monthlyTokenLimit` (default `1000000`, `0` = ilimitado). Funciones:
  - `getTokenBudget(workspaceId)` → `{ used, limit, pct, exceeded, status }` (status: `ok` | `warning` ≥90% | `critical` ≥95% | `exceeded`).
  - `assertTokenBudget(workspaceId)` — lanza `err.status = 429` + `code: TOKEN_BUDGET_EXCEEDED` si superado. Llamar antes de toda invocación a Claude.
  - `hasTokenBudget(workspaceId)` — versión booleana para crons (no lanza).
  - Se acumula vía `AiTokenLog` (inputTokens + outputTokens) en el mes calendario actual. Configurable por workspace desde SuperAdmin (`PATCH /api/superadmin/workspaces/:id/token-limit`).

- **Servicios de Marketing** (SerpAPI, Cannibalization, Social scrape de RRSS, Competitor snapshot, Marketing objectives engine) — ver `../docs/claude/marketing.md`.

**Búsqueda de texto — `lib/textSearch.js` (una sola forma para todo el producto):** `contains` + `mode: 'insensitive'` de Prisma es ILIKE: ignora mayúsculas pero **no tildes**, y exige la subcadena exacta. En español eso es un problema real — "perez" no encontraba a "Pérez", "diseno" no encontraba a "Diseño" y "posteos noviembre" no encontraba "Posteos de noviembre". `buildTextSearchFilters(q, fields)` devuelve las condiciones para un `AND`: **las palabras se combinan con AND** (cualquier orden, cualquier cosa en el medio) y **cada palabra tolera tildes**. `fields` es el nombre de una columna, un array de columnas, o funciones para los campos de una relación (`p => ({ company: { name: p } })`) — con varios campos, cada palabra puede aparecer en cualquiera de ellos.

- **Cómo tolera las tildes sin la extensión `unaccent`:** explotando una regla de la ortografía española — una palabra lleva **como máximo una tilde** —, así que las variantes de una palabra escrita sin tildes son **lineales** (una por vocal, más la ñ) y no combinatorias: para "internacionalizacion" son 15 patrones, no 2^14. Eso permite expresar la consulta con Prisma puro, sin `$queryRaw` ni migración.
- **Lo que esto NO es:** la solución canónica sigue siendo `unaccent` (o una columna normalizada generada con `translate`, que sí es inmutable) **con un índice de expresión**. Lo de acá hace más trabajo por consulta (N patrones ILIKE en vez de uno) sobre el mismo scan. En las tablas chicas y ya scopeadas por workspace no se nota; **si alguna búsqueda empieza a pesar — el candidato es `chat.controller.js` `searchMessages`, que barre el contenido de los mensajes de un canal — ese es el momento de pasar a columna normalizada + índice**, no de volver atrás.
- **Dónde se aplica:** buscador global (`search.controller.js`, las 4 entidades), búsqueda de tareas del MCP (`tasks/search.controller.js`), mensajes de chat, piezas de Contenido, archivos (equipo, portal del cliente y links públicos), Ventas (empresas y leads), Finanzas (clientes, facturas, items, movimientos), bandeja de WhatsApp, informes de Marketing y usuarios de SuperAdmin.
- **Dónde NO se aplica, a propósito:** los `equals` de email (login, invitaciones, alta de miembros) y los chequeos de nombre duplicado (categorías e items de Finanzas). Esos son lookups de **identidad y unicidad**, no búsquedas: plegar tildes ahí haría colisionar dos nombres que el usuario eligió distintos.
- **Espejo en el frontend:** `frontend/src/utils/textSearch.js` resuelve lo mismo para los filtros que corren en el browser, pero con la técnica directa (`normalize('NFD')` + borrar diacríticos en las dos cadenas), que ahí sí se puede porque las dos están en memoria. Ver `frontend/CLAUDE.md`.

**MCP (Grok) — `src/mcp/`:** servidor MCP montado en `/api/mcp`, con autenticación propia por token estático (`McpToken`, `mcp/auth.js`; no es el JWT de sesión). Las tools no duplican controllers: llaman a los endpoints REST de siempre por loopback (`mcp/apiBridge.js`), así heredan feature flags, permisos y gates. El catálogo de tools es declarativo (`mcp/toolCatalog.js`). **Antes de tocar `src/mcp/`, agregar una tool o cambiar algo que vean los agentes, leé `../docs/claude/mcp.md`**: tokens y revocación, los 401 que dejan rastro, identidad y nombre declarado del agente, novedades, canales de salida (aviso, webhook, despertador), respuestas livianas, guía y catálogo en vivo.
