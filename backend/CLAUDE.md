## Arquitectura backend

### Backend (`backend/src/`)
- **Express + Prisma + PostgreSQL.** Entry point `index.js` imports the Express app from `app.js`. Routes are mounted under `/api/<resource>`.
- **Auth:** JWT (12h expiry) stored in `localStorage`. Google OAuth 2 via `google-auth-library`. The `auth` middleware attaches `req.user` (decoded JWT payload).
- **Invariante de los JWT — un token de propósito acotado NO es un token de sesión.** `lib/jwt.js` `verifyToken` (compartido por el middleware `auth` y el handshake de Socket.IO) acepta **sólo** tokens sin el claim `purpose`, y todo JWT acotado firmado con `JWT_SECRET` lo lleva: `client-portal-live`, `client-portal-magic`, `google-link`, `oauth-state` (`lib/oauthState.js`, el `state` de Google/Meta/TikTok/LinkedIn) y `mfa` (`lib/mfaChallenge.js`, el paso intermedio del login con 2FA). **Al agregar un JWT que no sea de sesión: ponerle `purpose` y validarlo donde se consume.** Antes esto era una lista **negra** de un solo valor (`client-portal-live`), así que cualquier token acotado nuevo nacía sirviendo también como token de sesión: `resolveWorkspace` resuelve la membresía con el header `X-Workspace` + el `userId` del token, **no** con el `workspaceId` del token, así que bastaba con que trajera `userId` para habilitar todas las rutas de nivel `member` (las admin-only fallaban por falta del claim `role`). El `state` de OAuth era el caso más expuesto: viaja en el query string de la URL del proveedor. La inversión a lista blanca fue **prerrequisito** del 2FA — sin ella el `mfaToken` habría sido un bypass completo del segundo factor (contraseña → `mfaToken` → usarlo como Bearer). Tests en `tests/unit/tokenPurpose.test.js`.
- **Workspace middleware** (`middleware/workspace.js`):
  - `resolveWorkspace` — reads `X-Workspace` header → looks up `Workspace` → attaches `req.workspace` + `req.workspaceMember`. Requires an active `WorkspaceMember` row for **every** user, `isSuperAdmin` included — a super admin who isn't a member of a workspace gets 403 here, same as anyone else.
  - `workspaceAdminOnly` — verifies `req.workspaceMember.role === 'admin' | 'owner'`.
- **Super admin** — `User.isSuperAdmin Boolean` is a global flag. The `superAdminOnly` middleware in `superadmin.routes.js` gates the internal panel (`/api/superadmin/*`), completely separate from `resolveWorkspace`/`workspaceAdminOnly`. **`isSuperAdmin` never elevates a user's permissions *within* a workspace** — `workspaceAdminOnly`, `isSalesUser`/`salesGuard` (role part), `projectAccess.isAdmin`, `GET /auth/me`'s `isAdmin`, chat moderation, and lead-note deletion all key off the real `WorkspaceMember.role`, not `isSuperAdmin`. A super admin who happens to be a plain `member` of a workspace is treated as a plain member there — same as any other user. To act with elevated access in a workspace they don't belong to (or belong to with a lower role), staff must use **Impersonar** from the Super Admin panel (`POST /api/superadmin/impersonate`), which issues a token carrying the *target* member's real role and `isSuperAdmin: false`. The only remaining `isSuperAdmin` bypasses are orthogonal to workspace role: billing-status write locks (`past_due`/`suspended`, `resolveWorkspace`) and feature-flag gating (`requireFeatureFlag`, the flag-check inside `salesGuard`) — both let staff preview/operate a module regardless of billing or flag grants, but only once they've already cleared the (now un-bypassed) membership and role checks.
- **Tests:** Jest + Supertest. `jest.config.js` at backend root. All tests in `backend/tests/`. Prisma is mocked with `jest.mock('../lib/prisma')` — no real DB needed.
- All dates for workday logic use `America/Argentina/Buenos_Aires` (UTC-3). Task timestamps are stored in UTC.
- **Email** is sent via Resend HTTP API (`src/services/email.service.js`) — not SMTP. Every send (success or failure) is logged to `EmailLog`. Each email function accepts an optional `workspaceId` as last parameter for the log.
- **Prisma singleton** at `src/lib/prisma.js` — all controllers import from here.
- **Stripe singleton** at `src/lib/stripe.js` — returns `null` if `STRIPE_SECRET_KEY` is missing; all billing code checks for null before calling Stripe.
- **Prisma error helper** at `src/lib/prismaError.js` — `handlePrismaError(err, res)` maps P2025→404, P2002→409, P2003→400.
- **Shared utilities:** `src/utils/dates.js` exports `todayString()` (Buenos Aires timezone). `src/lib/monthUtils.js` exports helpers de meses (`monthBounds`, `prevMonthStr`, `prevMonthsArr`, `monthLabel`, y `periodMonths`/`periodLabel` para períodos calendario de objetivos). `src/lib/objectiveCatalog.js` es el catálogo único de métricas de objetivos (categoría, unit, direction, aggregation flow/stock, param requerido).
- **Shared task include:** `tasks/_shared.js` and `workdays.controller.js` each define a `taskInclude` constant (`{ project, createdBy, _count: { comments }, sessions, contentPiece: { select: { id, scheduledDate } } }`) used in all task queries. `contentPiece` is only non-null for tasks created via Contenido's "Enviar al dashboard" — `TaskCard.jsx`/`NowCard.jsx` use it to render a 📅 "Contenido · publica <fecha>" badge (urgent/red if `scheduledDate` is today or past, via `fmtPublishDate` in `utils/format.js`) linking to `/contenido?projectId=&piece=` (same URL shape as the `CONTENT_MENTION`/`CONTENT_APPROVED` deep-links in `NotificationBell.jsx`), so working the task and jumping straight to the piece doesn't require navigating Contenido → project → piece manually. `scheduledDate` also drives the Backlog's ordering (ver "Dashboard" en `../CLAUDE.md`): content tasks sort by nearest publish date first, ahead of the normal createdAt order.
- **Weekly AI report** at `src/services/weeklyReport.service.js` — generates productivity analysis with Claude Haiku, sent every Friday at 14:00 ART via `node-cron`. Sequential processing with 3s delay between users.
- **Insight memory** at `src/services/insightMemory.service.js` — weekly learning profile per user (tendencias, fortalezas, areasDeAtencion, estadisticas) using Claude Haiku. Updated every Saturday at 00:00 ART.
- **GEO audit** at `src/services/geoAudit.service.js` — fetches URL with axios + cheerio, analyzes with Claude (claude-haiku), stores result in `GeoAudit`. Async: controller returns auditId immediately, analysis runs via `setImmediate`. Progress tracked via `errorMsg` field during `running` status. Score 0–100 with 4 bands (Crítico/Base/Bueno/Excelente). Checks 23 AI crawlers (citation vs training), llms.txt, robots.txt, JSON-LD schema.
- **Feature flag catalog** at `src/config/featureFlags.js` — array of `{ key, name, description, stage }`. On server start, all flags are upserted to DB automatically. Never create flags manually from SuperAdmin UI — define them in code. `stage` separa dos paneles en SuperAdmin: `'module'` (estable, el sync de arranque fuerza `enabledGlobally=true` — panel **Módulos**, de solo lectura) vs `'testing'` (opt-in manual por workspace, panel **Feature Flags** de siempre). El controller (`featureFlags.controller.js` `update`) rechaza con 400 cualquier intento de tocar `enabledGlobally`/`enabledWorkspaceIds` de un flag `'module'`. Flags actuales: `marketing`/`eos`/`gamification`/`contenido`/`rrhh`/`calendario` en `'module'`; `ventas`/`whatsapp`/`finanzas` en `'testing'` (CRM y sus submódulos — WhatsApp de Ventas, y Finanzas — siguen en validación). `rrhh` ya traía `enabledGlobally:true` desde antes de existir `stage` (sembrado manualmente porque todos los workspaces ya lo usaban sin flag, ver concepto "RRHH panel") — con `stage='module'` ese estado queda estructural en vez de un seed manual.
- **Token budget** at `src/lib/tokenBudget.js` — presupuesto mensual de tokens de IA por workspace. `Workspace.monthlyTokenLimit` (default `1000000`, `0` = ilimitado). Funciones:
  - `getTokenBudget(workspaceId)` → `{ used, limit, pct, exceeded, status }` (status: `ok` | `warning` ≥90% | `critical` ≥95% | `exceeded`).
  - `assertTokenBudget(workspaceId)` — lanza `err.status = 429` + `code: TOKEN_BUDGET_EXCEEDED` si superado. Llamar antes de toda invocación a Claude.
  - `hasTokenBudget(workspaceId)` — versión booleana para crons (no lanza).
  - Se acumula vía `AiTokenLog` (inputTokens + outputTokens) en el mes calendario actual. Configurable por workspace desde SuperAdmin (`PATCH /api/superadmin/workspaces/:id/token-limit`).

- **Servicios de Marketing** (SerpAPI, Cannibalization, Social scrape de RRSS, Competitor snapshot, Marketing objectives engine) — ver `../docs/claude/marketing.md`.

**MCP (Grok) — integración (`src/mcp/`):** Servidor MCP (Model Context Protocol, SDK oficial `@modelcontextprotocol/sdk`) montado en `POST/GET/DELETE /api/mcp`, para que un cliente MCP remoto (hoy: Grok vía `grok.com/connectors` → Custom, pegando la URL + el Bearer token) pueda leer y escribir en BlissTracker. **Multi-usuario y multi-workspace desde el modelo** (tabla `McpToken`) — el alta/baja de un token es **self-service** desde el perfil propio, sin admin ni script. Arquitectura:
- **Modelo `McpToken`** (`{ workspaceId, userId, tokenHash, label, lastUsedAt, revokedAt }`, mismo patrón que `DeviceToken` de push notifications) — cada fila es UNA identidad fija: las tools ejecutan con el rol/permisos reales de esa membresía (nunca escalan) y las acciones quedan atribuidas a quien las hizo. `tokenHash` = sha256 del token plano (helper compartido `lib/mcpTokens.js`, `hashToken`/`generateToken`) — **el valor en claro no se guarda nunca**, solo se devuelve una vez al crearlo. Que cada fila cargue su propio `workspaceId` es lo que deja crecer a varios workspaces sin cambiar el modelo — hoy conviven todos los tokens en la misma tabla, agregar un workspace nuevo es simplemente dar de alta tokens con otro `workspaceId`, no una migración.
- **Autoadministración — Preferencias → "Agentes IA" (tab visible para todos, no solo admins)**: `frontend/src/pages/preferences/agents.jsx` muestra la URL del servidor MCP + un botón "Generar token" (con nombre/label opcional) que revela el valor en claro **una sola vez** en un modal con instrucciones de cómo pegarlo en Grok, y la lista de los propios tokens con botón "Revocar". Backend: `routes/mcpTokens.routes.js` → `controllers/mcpTokens.controller.js` (`GET/POST /api/mcp-tokens`, `PATCH /api/mcp-tokens/:id/revoke`), con la auth normal de sesión (`auth` + `resolveWorkspace`, no `mcp/auth.js`) scopeada a `req.user.userId` + `req.workspace.id` — cada usuario solo ve/gestiona sus propios tokens. Exento del bloqueo de escritura por `past_due` (`middleware/workspace.js` `PAST_DUE_WRITE_EXEMPT`, mismo criterio que `/api/profile`: revocar un token comprometido no debería depender de estar al día con el pago).
- **Revocación automática al desactivar un miembro**: `controllers/workspace/members.controller.js` `toggleMemberActive`, al desactivar (`active: true → false`), revoca (`revokedAt`) todos los `McpToken` no revocados de esa persona en el workspace, dentro de la misma transacción que reasigna tareas y lo saca de los proyectos. Reactivar el miembro **no** revive el token — hay que generar uno nuevo desde Preferencias. Doble capa de defensa: aunque algún camino futuro desactivara a alguien sin pasar por ahí, `middleware/workspace.js` `resolveWorkspace` ya rechaza con 403 cualquier request (incluida la del loopback de `apiBridge.js`) de un miembro con `active: false`.
- **Visibilidad global — SuperAdmin → "Agentes IA"** (`frontend/src/pages/superadmin/mcpTokens.jsx`, `GET /api/superadmin/mcp-tokens` en `controllers/superadmin/mcpTokens.controller.js`): tabla de solo lectura con TODOS los tokens de TODOS los workspaces (agente, persona, workspace, creado, último uso, activo/revocado) — para que el equipo de BlissTracker vea quién conectó qué sin tener que entrar a cada workspace.
- **Scripts de ops — `backend/scripts/mcp-create-token.js`/`mcp-list-tokens.js`/`mcp-revoke-token.js`** (uso interno por `WORKSPACE_SLUG`/`USER_EMAIL`/`TOKEN_ID`, mismo patrón que el resto de `scripts/`) — ya no son el único camino de alta (eso es Preferencias), pero siguen sirviendo para dar de alta/revocar en nombre de otra persona sin pedirle que lo haga ella.
- **`mcp/auth.js`** — autenticación propia del endpoint `/api/mcp` (no es el JWT de sesión normal): hashea el Bearer recibido y busca `McpToken.tokenHash`; 401 si no existe o está revocado. Actualiza `lastUsedAt` best-effort (no bloquea la request si falla). **Migración de compatibilidad automática**: si el token recibido coincide con el viejo `MCP_TOKEN` (env var, v1 de un solo workspace/usuario fijo por `MCP_WORKSPACE_SLUG`/`MCP_USER_EMAIL`) y todavía no tiene fila, se la crea sola la primera vez — así el conector ya configurado en un cliente sigue funcionando sin que nadie repegue un token nuevo. Esas 3 env vars quedan vivas solo para ese camino de compatibilidad; borrarlas de Railway una vez confirmada la migración es limpieza opcional.
- **Tareas de agente (`isAgentTask`) e identidad del agente**: `mcp/auth.js` agrega `tokenId` (el `McpToken.id`) a la identidad y `apiBridge.js` lo firma como claim `mcpTokenId` en el JWT interno — la API lo lee como `req.user.mcpTokenId` (helper `requestAgentId(req)` en `controllers/tasks/_shared.js`). No se puede falsificar desde afuera (solo se obtiene firmando con `JWT_SECRET`). Con eso: toda tarea creada vía MCP guarda `Task.createdByAgentId`; `task_create` con `executor:'agent'` crea una **tarea de agente** (`isAgentTask:true`, `agentId` = ese token; nunca asignable a otra persona — un agente trabaja solo para su dueño); `task_start` sobre una tarea delegada a "cualquiera de mis agentes" (`agentId` null) la asigna al agente que la toma. `tasks_agent_queue` (`GET /tasks/agent-queue`, `controllers/tasks/agents.controller.js`) es la lista de trabajo del agente (las suyas + las de `agentId` null; materializa recurrentes sin reabrir la jornada), con dos filtros opcionales: `?mine=true` (solo las del **nombre declarado** + las que no tiene nadie — el nombre sale de la identidad de la request, no de un query param, para no tener dos fuentes de verdad sobre quién llama) y `?from`/`?to` (ventana sobre la fecha efectiva del ítem: su `scheduledFor`, o el `workDay.date` si ya está activo; `to` default = hoy, que es el tope de siempre, y subirlo es la **única** forma de ver lo programado a futuro, que la cola esconde — sin parámetros el `where` es equivalente al de antes) y `task_set_executor` (`PATCH /tasks/:id/agent`, con `?scope=series`) delega/devuelve. `task_delete` (`DELETE /tasks/:id`, con `?scope=series`): vía MCP el `remove` de `lifecycle.controller.js` solo deja borrar tareas de agente **abiertas** del dueño que le tocan a ese agente (`isAgentTask`, `agentId` propio o null; en `series`, la plantilla también tiene que serlo) — 403 para tareas de personas aunque el dueño sea admin, 400 si ya está completada (es historial: métricas e informe al cliente). `getOrCreateToday` ya **no reabre** una jornada cerrada si la request viene por MCP. Ver concepto "Agentes IA (tareas de agente)" en `../CLAUDE.md`.
- **Novedades del agente — `tasks_agent_updates`** (`GET /api/tasks/agent-updates`, `agents.controller.js` `agentUpdates`, solo vía MCP: 400 sin `mcpTokenId`): un agente MCP no recibe avisos push (solo actúa cuando lo invocan), así que **esta bandeja es la única vía de vuelta hacia él**. Dos consultas en paralelo que se mezclan en un solo array `updates` ordenado por fecha del evento (`at`), cada ítem con `kind`, el estado actual de la tarea y sus últimos 3 comentarios:
  - `kind: 'completed'` — tareas con `createdByAgentId` = ese token que alguien completó y el agente todavía no vio (`Task.createdByAgentSeenAt` null). Si declaró `agentName`, solo las que creó con ese nombre. Excluye las que ejecutó él mismo. Trae quién la completó, cuándo y `workedMinutes` (`taskMins`). `completeTask` vuelve a poner `createdByAgentSeenAt` en null, así una tarea reabierta y recompletada vuelve a avisar. La migración `task_agent_updates` marcó como vistas las ya completadas, para que el primer llamado no trajera el historial.
  - `kind: 'unblocked' | 'comment'` — lo que la persona le dejó en SUS tareas de agente desde la app: la destrabó (`unblockTask`, rama `parked`) o le comentó algo (`comments.controller.js` `addComment`, solo si el comentario NO lo escribió un agente). Marcado con `Task.agentUpdateAt`/`agentUpdateKind` (migración `task_agent_update_inbox`), que el `markSeen` **limpia a null** en vez de sellar una fecha: es un "hay algo nuevo", no un "visto hasta acá". Si ya había una novedad sin ver, la nueva la reemplaza — el payload trae igual el estado y los comentarios, así que no se pierde información. El scope es el mismo que `agent-queue` (`agentId` propio o null, las delegadas a "cualquiera de mis agentes"), **sin** filtrar por `agentName`: es su lista de trabajo, y una tarea destrabada tiene que llegarle igual.
  Por default marca vistas las que devuelve (`?markSeen=false` solo lee). `INSTRUCTIONS` le pide al agente revisarla al conectarse, y la sección de tareas de la guía le dice qué hacer con cada `kind` (una `unblocked` se retoma con `task_resume`, no con `task_start`: la tarea quedó `PAUSED`).
- **Canales de SALIDA hacia el agente** (`services/agentNotify.service.js` los dispara desde un solo lugar; lo llaman `unblockTask` y `addComment` con `notifyAgentOfNewsInBackground`, en `setImmediate` para no demorar la respuesta de la persona). MCP es unidireccional: el agente nos llama, nunca al revés, y las notificaciones del propio protocolo no sirven (necesitan una sesión abierta que los clientes no mantienen entre conversaciones, y no se inyectan al contexto del modelo). Tres vías, de menos a más autónoma:
  1. **La bandeja** (`Task.agentUpdateAt`) — la escribe el controller, no el servicio de avisos: tiene que quedar marcada aunque los otros dos canales estén apagados o fallen. Es el estado, las otras dos son el empujón.
  2. **Aviso pegado a la respuesta de una tool** (`mcp/newsNudge.js`, mismo mecanismo que `workReminder.js`): si el agente tiene novedades sin ver, se le suman al final de la respuesta de cualquier tool. No lo despierta, pero deja de depender de que se acuerde de llamar a `tasks_agent_updates` — una conversación que arranca con "completá la tarea 12" nunca pasaba por ahí. **No marca nada como visto** (eso solo lo hace `tasks_agent_updates`): si el modelo ignora el bloque, el aviso vuelve al próximo intervalo, porque repetir es preferible a perder una novedad que nadie confirmó haber leído. Throttle de 10 min fijo en código y en memoria del proceso (no otra columna en `McpToken`), que **solo arranca si hubo algo que avisar**, así una novedad nueva no espera el intervalo entero. No se le pega a `tasks_agent_updates`, que ya devuelve todo.
  3. **Webhook firmado** (`services/agentWebhook.service.js`, `McpToken.webhookUrl`/`webhookSecret`): POST con `X-Bliss-Signature: sha256=HMAC(body)`, timeout 5s y un reintento (el caso típico es un receptor serverless dormido). Manda **solo el titular y el id de la tarea**, nunca el contenido del trabajo: el receptor va a buscarlo con el token del agente, que es lo que lo autoriza a leerlo — así un webhook interceptado no filtra nada y la URL no necesita ser secreta. La URL se valida con `assertPublicUrl` (`lib/safeUrl.js`) **dos veces**: al guardarla y antes de cada envío, porque un DNS puede cambiar de IP en el medio (SSRF por rebinding). El resultado de la última entrega queda en `webhookLastAt`/`webhookLastStatus` — eso reemplaza una tabla de log: lo que importa es "¿está funcionando?", no el historial. **No sirve con Grok en grok.com**: no hay endpoint que reciba.
  4. **El despertador** (`services/agentWake.service.js`, `McpToken.wakeEnabled`): el backend invoca al agente por la API del proveedor (`api.x.ai`, compatible con el function calling de OpenAI) con la API key del workspace (`Workspace.agentWakeApiKey`, **cifrada** con AES-256-GCM). Es el único canal que funciona sin que nadie invoque al agente. Corre con la **misma identidad** que el agente (su `McpToken`), así que hereda sus permisos reales y todo lo que hace queda atribuido a él (`createdByAgentId`, `TaskComment.agentId`) — las tools se ejecutan por el mismo `prepareRun` de `mcp/liveTools.js` + `apiBridge.callApi` que usa `bliss_run`, con la misma validación `strict`. El system prompt es `INSTRUCTIONS` tal cual, y entre las tools van `bliss_guide`/`bliss_tools`/`bliss_run` sintéticas, así el agente se comporta igual que un cliente MCP recién conectado sin duplicar las reglas en otro prompt. **No se le pasan las 168 tools del catálogo** (payload enorme): un set acotado por `WAKE_TOOL_RE` (tareas, archivos, `whoami`, `team_list`) + `bliss_run` para el resto. Topes: `MAX_STEPS` (8 tool calls por despertar) y un cooldown de 5 min por agente — cada despertar gasta la key del workspace, y varias novedades seguidas (destrabar + comentar) son un solo trabajo. Los tokens **no** pasan por `lib/tokenBudget.js`: ese presupuesto es de nuestra key de Anthropic, esta la paga el cliente. **Aviso importante para cualquiera que toque esto:** el agente que corre acá NO es el de grok.com — es un Grok nuevo por API, sin la configuración, las instrucciones ni la memoria del chat. Eso se le dice al usuario en la UI, no se asume que lo sepa.
  Configuración: `controllers/mcpTokens.controller.js` (`PATCH /api/mcp-tokens/:id` con `webhookUrl`/`wakeEnabled`, self-service) + `GET/PUT /api/mcp-tokens/wake-config` (la API key, **admin/owner**, porque la paga el workspace). UI en `frontend/src/components/preferences/agentChannels.jsx`. Tests en `tests/unit/agentOutboundChannels.test.js`; el cable desde el desbloqueo, en `tests/integration/agentTasks.test.js`.
- **"Registrá en qué estás trabajando" — `task_working_on` + recordatorio**: los agentes se olvidan de cargar lo que hacen, y BlissTracker no puede preguntarles (MCP va solo del agente hacia acá).
  - `task_working_on` es la primera tool **compuesta**: en vez de `request(args)` declara `run(args, call)` y encadena llamadas a la API. `runTool` de `server.js` soporta las dos formas, también vía `bliss_run`. Con `taskId` llama a `PATCH /tasks/:id/working-on` (`agents.controller.js` `prepareWorkingOn`, solo vía MCP). Ese endpoint trae a hoy una tarea planificada (`scheduledFor` futuro o Backlog) sin reabrir la jornada (`ensureTodayWorkDay`), se la asigna a este agente (una tarea de la persona pasa a ser de agente: 409 si ella la tiene en curso o si la tiene otro agente) y devuelve `next` (`start`/`resume`/`unblock`/`none`). La tool hace después ese paso contra el endpoint de siempre, así no se duplica la lógica de iniciar. Sin `taskId`: `POST /tasks` con `executor:'agent'` y después `start`.
  - **`task_log_done` — la otra mitad: lo que YA terminó.** `task_working_on` sirve cuando el agente arranca algo; cuando trabajó primero y registra después (el caso más común, y el que más errores y vueltas genera), la secuencia era crear/tomar → iniciar → completar → `task_set_duration`, y además **no había forma de registrarlo en el día en que se hizo**. `task_log_done` es compuesta igual que `task_working_on`: encadena esos endpoints de siempre (así hereda los efectos de completar — to-dos vinculados, piezas de Contenido, próximas acciones de Ventas, avisos — sin duplicar nada) y agrega un único paso propio, `PATCH /tasks/:id/logged-at` (`agents.controller.js` `setLoggedAt`, solo MCP). Ese paso mueve **las dos** marcas de tiempo que el producto usa para contar el trabajo: `workDayId` (el Dashboard y el historial filtran por `workDay.date`) y `completedAt` (Reportes/Productividad/el informe al cliente bucketean por ahí, ver `buildCompletedAtWhere`) — mover una sola dejaría la tarea contada en un día en una vista y en otro día en la otra. `startedAt` y las `TaskSession` se corren por el **mismo delta** en vez de recalcularse, así la tarea sigue durando lo que duró; `pausedMinutes` y `minutesOverride` no se tocan. La hora de cierre es las 18:00 de ese día en la tz del workspace (un final de jornada plausible, nunca en el futuro): lo que el agente declara es el día y la duración, no un horario que nadie midió. **Tope: el 1° del mes en curso** — el tiempo de agente consume las horas contratadas del proyecto y se le informa al cliente, así que un mes cerrado (informe generado, horas reportadas) no se reescribe; y solo sobre tareas de **agente** del dueño (403 sobre una tarea de la persona: su tiempo no se reescribe desde acá). Como a partir de `complete` la tarea ya quedó modificada, si falla un paso posterior la tool devuelve el error **con el `taskId` y qué quedó a medias**, para que el agente lo arregle en vez de volver a cargar todo y duplicar.
  - **Recordatorio** (`mcp/workReminder.js` `maybeWorkReminder`): después de cada tool que salió bien, si el agente no tiene ninguna tarea de agente `IN_PROGRESS` (de ese token y, si declaró nombre, de ese `agentName`), `runTool` suma un segundo bloque de texto. Ese bloque lista hasta 3 tareas planificadas para hoy, con su id, para que arranque una de esas en vez de crear otra. Sale como mucho una vez cada `McpToken.workReminderMins` (default 30; 0 = nunca; editable por token en Preferencias → Agentes IA vía `PATCH /api/mcp-tokens/:id`) por token + nombre, con estado en memoria del proceso. Nunca lanza. Migración `task_agent_work_reminder`; tests en `tests/unit/mcpWorkReminder.test.js`.
- **Nombre declarado del agente (`agentName`)**: varios agentes de un mismo cliente (ej. los de Grok) pueden compartir un token, y para BlissTracker serían uno solo. `mcp/server.js` le suma a TODAS las tools del catálogo un parámetro opcional `agentName` (`agentNameParam`, no hace falta declararlo tool por tool), lo saca de los args antes de `tool.request()` y se lo pasa a `callApi`. `apiBridge.js` lo normaliza (`sanitizeAgentName`: sin caracteres de control, espacios colapsados, ≤60) y lo firma como claim `mcpAgentName`. La API lo lee con `requestAgentName(req)` (`controllers/tasks/_shared.js`; solo cuenta si además hay `mcpTokenId`). Es **autodeclarado, no verificable**: es un rótulo, los permisos siguen siendo los del token. Se guarda al lado de cada FK a `McpToken`: `Task.createdByAgentName`/`agentName` (este último = quién la ejecuta; se actualiza cuando un agente con nombre la inicia/retoma/completa/bloquea, en `executorNameData` de `lifecycle.controller.js`; se limpia al delegar desde la app o al volverla humana), `TaskRecurrence` (se copian a cada instancia), `TaskComment.agentName`, `ProjectSituationEntry.createdByAgentName`/`updatedByAgentName`, `WhatsappMessage.senderAgentName` y `WhatsappConversation.agentControlName`. Se muestra como "<label del token> · <nombre>" con `formatAgentName` (`lib/agentTasks.js`, también en avisos y en el timeline del lead) y `agentName(agent, declared)` (`frontend/src/hooks/useMyAgents.js`). `computeAgentStats` (Productividad) agrupa por token + nombre declarado, así cada agente sale en su propia fila.
- **`mcp/apiBridge.js`** — en vez de duplicar controllers/middlewares (feature flags, `moduleAccessGuard`, proyectos privados, billing status, etc.), cada tool le pega por **loopback HTTP** (`http://127.0.0.1:$PORT/api/...`) a la propia API, con un JWT interno de vida muy corta (2 min, nunca sale del proceso) mintado al vuelo para el `userId`/`workspaceSlug` de la identidad resuelta por `mcp/auth.js` para ESA request — `callApi(identity, method, path, opts)` no conoce usuarios/workspaces fijos, por eso sirve igual para 1 o N de cada uno. Así hereda exactamente las mismas reglas de acceso que una request real del frontend, sin lógica nueva. `isSuperAdmin: false` siempre — el MCP nunca escala por encima del rol real de esa membresía.
- **`mcp/toolCatalog.js`** — catálogo declarativo: cada tool es `{ name, description, inputSchema (zod shape), request(args) → { method, path, query?, body? } }`, mapeado 1:1 a un endpoint existente (ver `../docs/claude/api-routes.md`). Para agregar una tool nueva alcanza con un objeto más en este array — no hace falta tocar `server.js`. v1 cubre (172 tools de catálogo + `bliss_guide`/`bliss_tools`/`bliss_run`): identidad (`whoami` → `GET /auth/me`: isAdmin + moduleAccess), proyectos (lectura —`list_projects` recorta la respuesta por default, ver abajo— + **estado de las conexiones** `project_connections` + **editar servicios contratados**, admin-only, reemplaza la lista completa; escritura: correr GEO audit, agregar/sacar keyword, agregar competidor, regenerar informe, **refresco masivo de fuentes** `marketing_refresh_run`/`marketing_refresh_status` — ver concepto "Refresco masivo de fuentes" en `docs/claude/marketing.md`), SEO avanzado (Canibalización/Content Brief/On-Page Audit/Content Gap/PageSpeed — con run+list+get(+delete salvo PageSpeed), mismo patrón; - **Respuestas livianas: el agente paga cada campo en tokens.** `GET /projects` devuelve la ficha completa de cada proyecto (links, redes, `integrationDefaults`, URLs protegidas de canibalización, secciones del informe, avatares del equipo) porque es lo que necesita la grilla de Mis Proyectos — unos **300 KB** en un workspace con 30 cuentas, de los que un agente usa el id, el nombre y los servicios. `list_projects` es la **única tool con post-proceso de la respuesta**: declara `run(args, call)` (la misma forma compuesta de `task_working_on`) y recorta con `compactProject`; `detail: 'full'` devuelve la respuesta tal cual. Se recorta en la tool y **no** con un `?fields=` en el endpoint para no cambiarle la respuesta al frontend, que sí usa el resto. Mismo criterio en `tasks_search`, que arma sus filas a mano en vez de reusar `taskInclude`. **Y el resto de las tools de tareas se recorta por `shape`**: cada entrada del catálogo puede declarar `shape: 'task' | 'tasks' | 'taskLists'` y `runTool` aplica `compactTask` a la respuesta — el proyecto pasa a `{id,name}` y el array de sesiones a `workedMinutes` ya calculado, conservando todos los campos propios de la tarea. Se hace con un hook declarativo y no convirtiendo 15 tools a la forma `run` por lo mismo de siempre: `taskInclude` trae `project: true` (la ficha entera, con los JSON de redes, defaults de integraciones y URLs protegidas) porque es lo que necesita el Dashboard, y eso no se toca.
- **`project_connections` — "no es que no haya datos, falta la conexión"** (`GET /api/marketing/connections`, `integrations.controller.js` `connectionsStatus`): `GET .../integrations` solo lista las integraciones que **existen**, así que un agente frenado porque falta Search Console no tiene cómo saber qué falta ni dónde se arregla. Devuelve el mismo cuadro que pinta el panel "Conexiones" de Prioridades (`active`/`expired`/`missing` por fuente) más el link de la app donde se conecta cada una; sin `projectId`, solo lo que falta de cada proyecto activo. El catálogo de fuentes vive en `lib/connectionCatalog.js`, **espejo de `frontend/src/components/marketing/ConnectionsPanel.jsx`** (mismo criterio que `contentCatalog.js`: mantener los dos en sync). `?state=all|pending|expired|missing` recorta por estado (`pending` = vencidas + sin conectar, el default cross-proyecto): sin filtro, un workspace con muchas cuentas sin conectar da decenas de KB. **`expiresAt` solo viaja si es una fecha FUTURA**: es el vencimiento del access token, que con refresh token (todas las de Google) se renueva solo cada hora, así que una fecha pasada al lado de `active` es lo normal — se informaba y se leía como alarma. Si el acceso estuviera caído de verdad, `status` sería `expired`. **El link es a la app, no a la URL de OAuth**: el `state` de los flujos OAuth vive 10 minutos (`lib/oauthState.js`) y el callback vuelve a una página puente que espera ser un popup abierto por la app, así que una URL de consentimiento pegada en un chat llega vencida y sin opener — lo único que sirve es la pantalla donde la persona aprieta "Conectar" y el flujo arranca fresco. La ruta **no cuelga de `/projects/:id`** (es cross-proyecto sin `projectId`), así que resuelve el gate de proyectos privados adentro del handler en vez de heredarlo de `requireProjectAccessPrefix`.
- **Equipo y Productividad (admin/owner-only, salvo `team_list`/`services_list`)**: `team_list` (sin restricción — mismo criterio que la UI, cualquiera ve el roster) lista nombre/email/rol/rol de equipo; las cuentas asignadas a cada persona se cruzan con `list_projects` (cada proyecto ya trae su equipo vía `members`). `team_attendance` reusa el `userSummary` de RRHH (entrada, horario pactado, tardanza, puntualidad — **sin hora de salida**, el producto no trackea logout). `team_task_history` es un endpoint nuevo (`GET /api/admin/productivity/tasks`, no agregado como el resto de Productividad): tareas con título/proyecto/responsable/estado/fechas/duración real (vía `TaskSession`, mismo `taskMins` que el resto de la app) y pausas con fecha (sin motivo — solo bloquear lo pide, y el motivo de bloqueo solo persiste mientras la tarea sigue bloqueada, no hay historial de bloqueos pasados); **no tiene "fecha límite" ni "duración estimada"**, el producto no captura esos datos. `tasks_today` ahora acepta `userId` opcional: sin él, la jornada propia (igual que siempre); con el de otra persona, una vista de **solo lectura** admin-only (`getForeignToday` en `workdays.controller.js`) que deliberadamente NO reusa el flujo normal — ese crea el `WorkDay` si falta, lo **reabre** si ya estaba cerrado y materializa tareas recurrentes, efectos secundarios correctos para el dueño de la jornada pero un bug si los dispara alguien solo mirando. `project_update_services` (`PUT /projects/:id` con body `{serviceIds}` únicamente, el resto de campos del endpoint no se tocan) reemplaza la lista COMPLETA de servicios — no es aditivo, hay que mandar el array entero (leer antes con `list_projects`/`services_list`). "Responsable de un objetivo de marketing" no es un campo que exista — el equipo del proyecto (`list_projects`.members) hace ese rol.
- **Nube del proyecto vía MCP (lectura y escritura sin browser)**: el flujo normal de Archivos es presign → PUT directo a R2 desde el browser → confirm, que un agente no puede hacer (un tool-call manda y recibe JSON, no bytes). Dos endpoints cubren eso sobre el MISMO repositorio y las mismas validaciones (nada de un storage paralelo): **`POST /api/projects/:id/files/direct`** (`projectFiles.controller.js` `directUpload`) sube desde el servidor con `content`/`contentBase64`/`url` y resuelve la carpeta destino por `parentId` o por `folderPath` (`"Informes/2026"`, se crea nivel por nivel con `findOrCreateFolder` de `lib/projectFileTree.js`; se resuelve **después** de validar los bytes para no dejar carpetas vacías si el archivo se rechaza), y **`GET /api/projects/:id/files/:fileId/content`** (`readFileContent`) devuelve el archivo como **texto** — texto/markdown/CSV/JSON/XML tal cual, PDF y DOCX vía `lib/documentText.js`, truncado a 200k caracteres (`truncated`), 415 (`NOT_TEXT_READABLE`) para imágenes/video/binarios y 413 arriba de 30MB. La resolución de bytes + tipo real del "direct upload" vive en **`lib/directUpload.js`** (`resolveDirectUpload`: una sola fuente, tope de 25MB, descarga de URL con `assertPublicUrl` en cada redirect por SSRF, magic bytes → MIME declarado → Content-Type → extensión, denylist), compartida con `tasks/attachments.controller.js` `directAttachment` — lo único que cambia entre los dos es la carpeta destino y el `TaskFile` que uno crea y el otro no. `lib/documentText.js` (`extractText`, PDF con pdf-parse v2 + DOCX con mammoth) se extrajo de `services/whatsappBotDocument.service.js`, que lo sigue usando igual. Las tools de borrado/movimiento (`project_file_update`/`_delete`) pegan a los endpoints de siempre: borrar es soft-delete a la papelera (reversible con `project_file_restore`), y purgar sigue siendo admin-only desde la app.
- **`mcp/guide.js` — onboarding del agente**: `INSTRUCTIONS` viaja en el handshake `initialize` (opción `instructions` del `McpServer`, el cliente la inyecta sola en el contexto del modelo) y le pide leer `bliss_guide` + `whoami` antes de actuar. `bliss_guide` (registrada a mano en `server.js`, no pega a la API) devuelve la guía completa o una sección (`topic`): permisos, reglas del negocio, qué confirmar antes, y qué NO está disponible por MCP. El índice de tools de cada sección se arma solo desde el catálogo (por prefijo de nombre, `AREAS`); las reglas y la lista de "no disponible" son texto a mano — **al agregar tools o módulos al MCP, actualizar `guide.js` y la categoría "Agentes IA (MCP)" del Wiki** (`frontend/src/data/wikiContent.js`). `tests/unit/mcpGuide.test.js` falla si una tool del catálogo no aparece en la guía.
- **`mcp/liveTools.js` — `bliss_tools` + `bliss_run` (catálogo en vivo):** algunos clientes guardan la lista de tools al configurar el conector y no la vuelven a pedir (**Grok la guarda por URL**: ni reconectar la refresca; cambiar la URL, ej. `?v=2`, sí). Para que una tool nueva se pueda usar apenas se deploya: `bliss_tools` (registrada a mano en `server.js`) devuelve el índice del catálogo de ESTE deploy agrupado por las `AREAS` de `guide.js` (`query` filtra; `tool` da descripción + parámetros en JSON Schema, convertidos con el mismo `toJsonSchemaCompat` del SDK que usa `tools/list`), y `bliss_run({ tool, args, agentName? })` ejecuta cualquier tool del catálogo por nombre: valida `args` con su zod shape en modo `strict` (un parámetro mal escrito da error con los parámetros correctos, no se ignora; `args` también se acepta como string JSON y `agentName` dentro de `args`) y corre por el mismo `runTool` que las tools registradas — mismos permisos, mismo loopback. `INSTRUCTIONS` le pide al agente revisar `bliss_tools` antes de decir que algo no se puede. Tests en `tests/unit/mcpLiveTools.test.js`.
- **`mcp/server.js`** — registra el catálogo contra un `McpServer`, un handler genérico por tool (llama `apiBridge.callApi(identity, ...)` y devuelve `{ content: [{ type:'text', text: JSON del response }], isError: status>=400 }`). `buildServer(identity)` cierra cada tool sobre la identidad de ESA request (nunca una global), así dos personas (o dos workspaces) en paralelo no se pisan. Transporte **Streamable HTTP con sesiones**: cada `initialize` abre una sesión (header `Mcp-Session-Id`, guardada en memoria en el Map `sessions`, atada al `tokenId` que la abrió; con otro token → 404). Sirve para que los clientes vean las tools nuevas sin reconectar a mano: un deploy reinicia el proceso, las sesiones viejas desaparecen y el próximo request con un id viejo recibe **404**, que según la spec obliga al cliente a reinicializar y volver a pedir `tools/list` (el SDK ya declara `tools.listChanged: true`; la notificación no se manda porque la lista no cambia dentro de un mismo proceso). Sesiones inactivas >1h se barren cada 10 min, tope de 500 (se cierra la más vieja). Un request **sin** session id que no es `initialize` se sigue atendiendo en modo stateless (instancia nueva por request, como antes), así un cliente que no guarda el id no se corta. Asume **una sola instancia** del backend (igual que los locks de los crons): con varias réplicas sin sticky sessions, una sesión abierta en una daría 404 en la otra. Tests en `tests/integration/mcpSessions.test.js`.
- Sin OAuth: cada cliente MCP necesita un Bearer token estático (generado desde Preferencias), no hay authorization server OAuth 2.1 con dynamic client registration ni consentimiento granular por scope — deliberadamente fuera de alcance; el token ya hereda el rol real de quien lo generó, que es el control de acceso que importa.
