# Frontend — BlissTracker

Convenciones específicas del frontend (React 18 + Vite + Tailwind). Se carga automáticamente cuando Claude Code trabaja dentro de `frontend/`. Los conceptos de dominio (Ventas, Marketing, WhatsApp, etc.) están en `../docs/claude/` — este archivo es solo arquitectura e infraestructura frontend. Ver también `../CLAUDE.md` (raíz) para el proyecto en general.

## Environment variables (`frontend/.env.development`)
```
VITE_API_URL=http://localhost:3001
VITE_GOOGLE_CLIENT_ID=xxxx.apps.googleusercontent.com
```

## Arquitectura frontend

### Frontend (`frontend/src/`)
- **React 18 + Vite + Tailwind CSS + React Router v6.**
- **Color palette:** Custom `primary` tokens in `tailwind.config.js` based on orange (#F7931A). Status colors: IN_PROGRESS = primary (orange), PAUSED = gray, BLOCKED = red, COMPLETED = green, PENDING = gray.
- **Tests:** Vitest + React Testing Library. Test config in `vite.config.js` (`test` block). All tests in `src/tests/`.
- `api/client.js` — Axios instance: reads `VITE_API_URL`, injects JWT from `localStorage`, injects `X-Workspace: <slug>` header (derived from `window.location.hostname`), redirects to `/login` on 401.
- `context/AuthContext.jsx` — global auth state; validates token on mount via `GET /auth/me`. Exposes `updateUser()` and `switchWorkspace(slug)` (re-issues JWT for the target workspace).
- `context/WorkspaceContext.jsx` — workspace info (name, slug, status, subscription). Loaded from `GET /api/workspaces/current`. Exposes `trialDaysLeft` (derived from `trialEndsAt`) and `isSubscriptionActive`.
- `context/ThemeContext.jsx` — dark mode toggle persisted to `localStorage`.
- `hooks/useRoles.js` — fetches `UserRole` list for label lookups. Module-level cache (once per session).
- `hooks/useInactivity.js` — tracks mouse/keyboard activity; auto-pauses after 120+10 min idle on an IN_PROGRESS task.
- `utils/format.js` — shared `fmtMins()`, `activeMinutes()`, `completedDuration()`.
- `utils/linkify.jsx` — converts plain URLs in text to clickable `<a>` tags.
- **Íconos: `components/ui/Icon.jsx` + `lucide-react` (set único de íconos de línea).** Convención: **sin ícono por defecto** — títulos, pestañas, botones con texto y secciones van solo con la palabra; el ícono se usa solo donde agrega información o reemplaza texto por falta de espacio (botones solo-ícono como cerrar/editar/eliminar, filtros de la campana, metadatos compactos como recurrente / adjuntos / comentarios, avisos). `<Icon as={Repeat} size={14} />` hereda `currentColor` y usa trazo 1.75. **No usar emojis como ícono de UI**; los emojis quedan solo en contenido del usuario (chat, reacciones, mensajes del sistema). `lib/moduleCatalog.js` guarda los íconos de módulo como componentes de lucide (`SetupHintCard`/`SegmentCards` los renderizan con `Icon`). Migración por fases: Fase 1 (menú, campana, buscador, Dashboard, ficha del proyecto, botón flotante, banners, onboarding) y Fase 2 (Marketing, informe del cliente y su PDF: tarjetas/catálogos sin ícono, métricas compactas con íconos de línea — likes, comentarios, alcance —, posiciones del top como número en vez de medallas, sellos de Meta/Google Ads con `Megaphone`, rótulos de Prioridades sin emoji también en el backend) y Fase 3 (Ventas —línea de tiempo del lead con íconos de línea por evento—, WhatsApp, RRHH, Contenido —contacto del cliente marcado con `Handshake`—, portal del cliente, Preferencias, Admin y la Nube del proyecto; `lib/fileIcons.js` `iconFor()` ahora devuelve un componente de lucide por tipo de archivo, se renderiza con `<Icon as={iconFor(mime)} />`), Fase 4 (EOS, Gamification, Calendario, SuperAdmin) y una pasada final por el resto de la app (chat y salas de voz, reuniones, reportes, actividad, pantallas de cuenta) hechas: la migración está completa. Quedan con emoji a propósito solo el contenido: los catálogos del chat (`emojiData.js`, `quickReactions.js`), Docs/wiki, las guías "¿Cómo se usa?" y las páginas públicas de marketing (Landing/Pricing/Solution*). Los símbolos de texto (✓ → ↑ ★) siguen siendo texto, no íconos. `utils/twemoji.js` queda solo como respaldo del PDF para emojis del contenido escrito por el equipo o la IA.

### Navbar — single source of truth
`Navbar.jsx` defines four arrays that are the single source of truth for both desktop and mobile navigation. Adding an item to any of these automatically appears in both views without duplication:
- `links` — main nav links (Dashboard, Mis Proyectos, Actividad, Mis Reportes para no-admin).
- `moduleSublinks` — items under el dropdown **"Módulos"**: Ventas, Marketing, Contenido, RRHH (en ese orden). **Siempre agrupados, nunca se aplanan al nivel superior aunque quede uno solo activo** — la posición de cada módulo en el menú es estable sin importar qué otros estén prendidos en el workspace (evita que un ítem "salte" de lugar cuando el admin activa/desactiva otro flag). Cada uno combina el feature flag correspondiente (`useFeatureFlag`) con el acceso por rol resuelto en `user.moduleAccess.<key>` (ver concepto "Acceso a módulos por rol") — el admin siempre lo ve, ese chequeo ya viene resuelto desde el backend. "Ventas" mantiene su condición histórica `useFeatureFlag('ventas') && (isAdmin || user?.isSales)` (equivalente a `moduleAccess.ventas`, se dejó así para no tocar el resto de sus consumidores) con el mismo criterio de destino que `NotificationBell`/`SetupChecklist`: `/admin/ventas` para admin, `/ventas` para el resto (ver concepto "Ventas (CRM)"). "RRHH" (`/admin/rrhh`, ver concepto "RRHH panel") es el módulo más reciente en sumarse acá — a diferencia de EOS/Gamification, expone datos personales sensibles (legajos) a cualquier rol al que se le dé acceso, decisión explícita. El dropdown entero no se renderiza si `moduleSublinks` queda vacío. Mismo patrón visual/interacción que `adminSublinks` (botón + chevron + panel absoluto en desktop, acordeón en mobile), con su propio estado (`modulesOpen`/`modulesMobileOpen`) y ref (`modulesRef`) para click-outside. **EOS y Gamification NO están acá** — quedaron estrictamente admin-only (ver `adminSublinks`), decisión explícita: datos sensibles (evaluaciones de personas) o funciones de gestión (crear/editar juegos y puntajes) que no deben poder abrirse a otros roles por error de configuración.
- `adminSublinks` — items under the "Administración" dropdown: **Reportes**, **EOS** (condicional a `useFeatureFlag('eos')`), **Gamification** (condicional a `useFeatureFlag('gamification')`) y **Panel** (Productividad se fusionó como tab dentro de RRHH, sin link propio; Ventas/Marketing/Contenido/RRHH viven en `moduleSublinks` por tener acceso configurable por rol; EOS/Gamification son un caso aparte: estrictamente `isAdmin`, sin acceso configurable).
- `profileSections` — items in the user profile menu (Perfil, Docs, Preferencias, Facturación, Super Admin, workspace switcher, logout). "Facturación" visible only for `isAdmin` (admin/owner). Rendered by `renderProfileSections(onClose)` which is called both for the desktop dropdown and the mobile panel.

**Atajos de teclado globales:** `GlobalShortcuts.jsx` se monta una sola vez en `App.jsx` (dentro de `<BrowserRouter>`, después de `<Routes>`) y maneja atajos para todo usuario autenticado en un subdominio de workspace (`enabled = !!user && isWorkspaceSubdomain()`). Maneja únicamente: `N` → nueva tarea (renderiza un `AddTaskModal` global, sin proyecto bloqueado), `?` → overlay de ayuda (catálogo agrupado en Tareas / General), `Esc` → cierra la ventana abierta. **Se sacaron los atajos de navegación** (`Shift+D/Y/A/M/R` a Dashboard/Proyectos/Actividad/Marketing/Reportes) **y las acciones de tarea con Shift** (`Shift+I/C/P/B`, que vivían en `Dashboard.jsx`) — en la práctica no se usaban; simplifica ambos componentes y evita mantenerlos sincronizados con el menú/la UI. El catálogo de ayuda también lista, **solo como documentación**, un atajo manejado por otro componente: `Ctrl/Cmd+B` (pizarra, en `NotesBoard.jsx`).

**Buscador global (Cmd/Ctrl+K, `CommandPalette.jsx`):** navegación (`useNavDestinations`), proyectos, personas, canales de chat (`useChat().channels`, abren el widget vía `bliss:open-chat`), leads/empresas de Ventas, servicios/roles (solo admin → `/admin?tab=`), **acciones rápidas** (nueva tarea, agendar reunión, abrir chat, cambiar tema — se listan sin escribir) y un bloque server-side `GET /api/search?q=` (`search.controller.js`: tareas, piezas de Contenido, reuniones de Calendario y archivos de proyecto; Contenido/Calendario respetan flag + `moduleAccess`, Archivos `Project.filesEnabled`). Elegir una tarea dispara `bliss:open-task` (lo escucha `GlobalShortcuts` y abre `TaskCommentsModal` sin navegar, también para tareas completadas). Deep-links que consume: `/calendario?event=<id>` / `?schedule=1`, `/admin/ventas?tab=empresas&company=<id>`, `/my-projects/:id?infoTab=archivos&fileId=`, `/contenido?projectId=&piece=`.

**Sin atajos de acciones de tarea:** `Dashboard.jsx` tenía un listener propio para `Shift+C/P/B/I` (completar/pausar/bloquear/iniciar la tarea en curso) — se eliminó junto con los de navegación de `GlobalShortcuts` (mismo motivo: en la práctica no se usaban). Las acciones de tarea se disparan solo desde los botones de `TaskCard`. Cuando se crea una tarea desde el modal global, `GlobalShortcuts` emite el evento `window` `bliss:task-created` (detalle = la tarea); `Dashboard.jsx` lo escucha y recarga con `loadToday()` (el botón "+ Agregar tarea" del propio Dashboard usa su modal local y **no** emite el evento, así no hay doble refresco).
